# 上游中心运行说明

上游中心 API 仅注册在管理员路由 `/api/v1/admin/upstream-center`。厂家的 Key 分组和独立监控共用目标配置与探测实现，但与现有渠道监控 V1/V2 开关、公共展示设置相互独立。

## 手动显示顺序

管理员可以通过 `PUT /api/v1/admin/upstream-center/order` 保存完整列表的顺序，请求为 `{ "scope": "suppliers" | "monitors" | "groups", "supplier_id": 123, "ids": [3, 1, 2] }`。仅 `groups` 必须携带正整数 `supplier_id`，其他范围不携带；`ids` 必填且必须是正整数、无重复，并涵盖该范围全部未归档记录。空范围允许 `[]`。非法输入返回 400 / `MANUAL_ORDER_INVALID`；记录新增、删除、移到其他范围等导致集合过期时返回 409 / `MANUAL_ORDER_CONFLICT`，客户端应刷新后重新排序。成功返回通常的 `data: null`，重新读取 overview 可取得已保存顺序。

迁移 `251_upstream_manual_order.sql` 添加三个可空 `sort_order` 列（厂家、监控目标、智商计划）。没有手动排序时完全保留旧列表顺序；已排序的记录按位置展示，新记录或跨列表移入的记录排在其后。厂家内的分组顺序、独立监控顺序与厂家顺序互相独立。API 不公开排序字段，以列表响应的数组顺序为准。

排序只改 `sort_order`，不改 `updated_at`、账号绑定、凭据、财务、检测时间、启停或运行快照，不产生任何上游请求。事务按列表串行排序，成员创建/归档/移组通过共享/排他 advisory lock 与完整集合验证协调，避免新增幻行或跨范围并发污染。正在检测或生成的卡片仍可排序；不要求暂停任务。

## 探测和记录

- 普通厂家 Key 分组、独立监控新建默认模型为 `gpt-5.6-sol`，默认每 30 秒一次，允许 30–3600 秒；每个模型独立请求、独立记录，最多 8 个模型。单模型超时允许 5–45 秒，默认 45 秒。迁移 `248_upstream_monitor_defaults.sql` 仅调整新建默认值与间隔约束，已有目标的模型、间隔和智商/OAuth 计划保持原配置。
- 新建启用目标在 5 秒轮询内进入检测；每个实例最多 5 个目标同时执行。PostgreSQL 条件租约排除跨实例及手动/自动检测重叠，租约 10 分钟，常规运行上限 7 分钟。
- 多模型按配置顺序检测。一次轮询完成后，下一次检测时间从完成时开始计算。暂停目标可以手动检测，完成后仍保持暂停。
- 活动探测期间，目标配置修改及归档返回 409，避免已发生的请求结果和费用因改配置丢失。管理员断开请求后，已完成的探测仍尝试写入记录；服务停止会取消探测并等待记录写入。
- 正常/波动均计为可用样本；失败和错误计为不可用。慢阈值默认 6000 毫秒。延迟是完整响应耗时，平均值与 P95 仅统计成功样本，不是首字延迟。
- 可用率支持 24 小时、7 天、30 天；另提供固定 7 天 `availability_7d` 给卡片展示，不随选择窗口变化。时间条独立展示该模型最近 60 次记录，旧到新排列，不混合模型。无样本为 `null`，不伪造 100% 可用。
- `latest_latency_ms` 为最新检测记录的延迟，包含失败记录；最新记录缺失延迟就返回 `null`，不回退至旧样本。卡片成功率复用渠道监控的连续红黄绿配色。60 条记录沿用 22px 高的原样式，各条宽度自适应铺满所在区域，悬停用现有 HelpTooltip 展示并复制已保存诊断；独立监控保留小卡和一行紧凑成功率/延迟指标。
- 页面「上次更新 N 秒前」每秒更新，是浏览器根据所选模型 `last_checked_at` 计算的时间差，不改变后台请求频率。

## 凭据和归属

API Key 使用项目已有 AES-GCM 密钥加密，接口仅返回掩码。请求仅允许公网 HTTPS，提交时校验 DNS/IP，实际建连再次校验并拒绝重定向；监控记录仅保留脱敏、截断后的具体错误摘要，不保存完整原始错误响应。

厂家分组与独立监控均在创建后排入首次余额/倍率同步，包括手动填写 URL + Key 和从 API Key 账号导入的独立监控。后台每 10 秒检查到期目标，每次同步完成后约 1 分钟再次同步，与 30 秒可用性探测间隔独立。同步复用 `/v1/usage` 中的 Billing，缺失时读取 `/v1/sub2api/billing`；仅保存上游明确返回的真实倍率，支持零倍率，缺失或不支持保持未知，不补成 1×。更换地址、Key、厂家或钱包身份会重新排入首次同步。Overview 只读本地快照，不触发外部网络请求；同步结果和错误在后续页面刷新中显示。

厂家分组可关联多个现有 API Key 账号，所有账号必须与分组使用相同 endpoint 和 Key。每个账号只能有一个活动归属。保存时在事务中再次锁定并校验账号凭据，避免并发修改造成错误归因；重复 endpoint+Key 的活动厂家分组会被拒绝。

独立监控可通过仅输入的 `source_account_id` 导入现有 API Key 账号。保存时由后端读取账号凭据，加密复制到新监控，不返回明文、不持久化来源关系、也不创建业务账号绑定；`account_ids` 必须为空。来源必须为启用且可调度开关打开、未自动过期的实际 API Key 账号，不能使用影子/合成测试账号或空 Key。显式传入的地址、平台必须与来源匹配，缺省时从来源补齐；`source_account_id` 与非空 `api_key` 同传会被拒绝。前端手动改地址、平台、Key 时清除待导入来源；编辑再次选择来源才重新复制，普通编辑保留已保存的 Key，不因原账号改动暗中换 Key。模型发现可以使用 `account_id` 读取新来源模型，来源优先于编辑中的旧 `target_id`，并应用相同来源校验。

现有目标更换地址或平台时，后端禁止自动沿用旧 Key；必须显式填写 Key、导入新来源，或使用与新地址、平台和 Key 精确匹配的厂家绑定账号凭据。取消待导入来源而保留新地址的表单也遵守这一约束，避免把旧 Key 发送至另一个上游。只改名称、模型、周期、暂停状态，或地址只增加末尾斜线时可以保留原 Key。源账号跨平台导入且未显式提供 `api_mode` 时重置为通用默认，避免沿用不兼容的 Responses 模式。

绑定使用有效时间区间；业务消费按 `usage_logs.created_at`（完成记账时刻）匹配归属。改 Key、改厂家、解绑或归档均关闭旧区间，保留旧账。厂家 ID、厂家名称和目标名称在绑定及监控记录中保留快照。正在进行的请求在绑定变更后完成时，按完成时的有效归属记账，因此属于账面估算。

## 成本与保留

### New API 上游

普通地址 + API Key 会先识别 Sub2API；接口不支持或返回不兼容认证响应时，再识别 New API 的 `GET /api/usage/token/`。仅接受明确的 `token_usage` 成功响应，读取当前 Key 的剩余额度、累计消耗和无限额度标记。Key 额度与账户钱包分开显示，不把无限额度当作余额为零。金额使用 `/api/status` 返回的 `quota_per_unit` 换算为系统 USD 额度；不使用充值价格或显示汇率。单位缺失、无效或换算溢出时保留原始 `QUOTA`，不猜测固定换算比例。

读取账户钱包和真实分组倍率需要在分组／独立监控的「New API · 余额与倍率授权」中填写该上游的用户 ID 和个人访问令牌（控制台访问令牌，不是模型 API Key）。新版 New API 接受 Bearer PAT，旧版同时要求 `New-Api-User`；这里始终发送两者。只执行读取接口：`/api/user/self`、`/api/token/search`、`/api/token/:id`、`/api/user/self/groups`。精确查到当前 Key 且所有用户 ID 匹配后才采用账户钱包；Key 分组为空时继承用户分组，倍率读取带用户覆盖的 `/self/groups`，不把公开报价当作个人实际倍率。`auto` 分组显示动态倍率并清除旧的固定倍率，缺失倍率保持未知，零倍率有效。智商监控选择这些上游分组时复用相同的实时快照。

New API 普通 Key 额度端点的官方默认限流为同 IP 20 次／20 分钟。成功读取后，Key-only 额度约每 20 分钟同步，并按站点限制请求速率；此间隔不影响可用性检测。启用控制台授权后跳过该端点，按原有约 1 分钟周期同步；首次精确查询后缓存经过归属验证的 Token ID，后续读取 ID 接口，减少搜索限流。缓存按站点、Key、用户 ID 和控制台凭据身份隔离，凭据变更不会复用旧结果。余额同步总请求预算 45 秒，小于 60 秒租约。

New API 不提供可靠的 Key 级完整今日费用接口，最近日志的条数有上限，不能冒充全天统计。因此上游报告的今日消耗保持未知，本站业务金额、请求数与 Token 统计继续使用现有账本；累计消耗仅取该 Key 的统计。共享钱包按站点、用户 ID、钱包标签和币种去重，不将不同用户的钱包合并，也不将多个 Key 的同一个钱包相加。

迁移 `253_upstream_newapi_credentials.sql` 仅追加可选加密凭据、无限额度字段及倍率来源类型。响应只返回用户 ID 与是否已授权，不返回控制台令牌或密文。修改地址、平台或用户 ID 必须重新填写令牌或明确关闭授权；修改凭据立即安排同步，写入时校验凭据身份。精确搜索 API 的查询包含 Key，因此本地错误和快照不得保存原始请求 URL 或完整上游响应。所有请求仍使用同一公网 HTTPS／DNS 复核和禁重定向客户端。

接口契约核对版本：官方 QuantumNous/new-api `v0.10.8`、`v1.0.0-rc.40`（`0aec08fee811ec6136828fda790551b49e410301`）。第三方修改版关闭这些读取接口时，页面展示具体缺失能力，不推算余额或倍率。

探测响应提供完整 token 使用量时，财务服务按账号采购配置或默认模型定价估算监控费用。未返回完整 token 计数或无定价时费用为未知，利润不会把这些请求当作免费。用户消费为账面额度消费，不代表现金收入。

同一厂家内，`wallet_ref` 表示运营者配置的共享钱包身份。共享 wallet 按同 ref、同 currency 选取最新的真实余额观测，金额、来源 Key、同步时间与状态一起保留，从不把多个 Key 的余额相加。已有同名钱包时，另一个 Key 的 401、待同步或不支持响应不会额外产生一个钱包；各 Key 的 `target.balance` 仍保留其原始失败状态。尚无任何可信钱包余额时保留未知占位，不伪造零。明确的 `key_quota`、`subscription` 按 Key 隔离，不同币种也不合并。多个实际独立的钱包应配置不同 `wallet_ref`。

监控采购估价比较所有绑定账号及其分组的可识别价格。自定义成本与默认成本冲突时，或渠道要求使用实际客户账单定价而直接探测没有该账单时，费用保持未知，不任取一项生成精确利润。

业务账目 `upstream_finance_ledger.total_tokens` 保存输入、输出、缓存写入与缓存读取之和。迁移 `247_upstream_finance_usage_totals.sql` 从仍存在且匹配的使用日志回填；原日志已清理而无法恢复的旧账保留 `NULL`。汇总有任何未知记录时 `total_tokens=NULL` 并返回 `unknown_token_requests`；没有业务请求时为零。UI 以 M 显示，达到十亿时换为 B，同时保留 `request_count` 业务请求数。Key 行右侧财务金额使用纯数字，币种在 title/详情中保留；这只是格式变化，不改变 API 金额单位或会计口径。

`account_billed` 返回业务账目历史账号计费之和，当前与 `business_cost` 相同：`COALESCE(account_stats_cost,total_cost) * COALESCE(account_rate_multiplier,1)`。零倍率有效，来源为记账快照，不依赖账号当前配置。它不是用户 `actual_cost`，也不包括监控费用。

### 存储清理与永久删除

存储管理默认启用自动保留策略：可用性监控明细保留 30 天，余额／倍率快照完整保留 7 天。管理员可将监控明细调整为 30–365 天、快照调整为 1–90 天；关闭自动清理后仍可手动执行一批清理。后台按小时检查，存在积压时每分钟续跑有界批次；每批每张表最多删除 5000 条、事务最长 30 秒，并使用数据库事务锁避免多实例同时清理。不会在启动时整档永久删除，也不会为了释放空间执行 `VACUUM FULL`。

监控明细到期前，先按 **UTC 整小时、检测时的目标与厂家归属**汇总监控成本、未知费用数量和费用来源数量，再在同一事务删除对应原始明细；重复运行不会重复计费。保留边界向下取整到 UTC 小时，完整保留边界小时，因此 7 天／30 天可用率与明细统计仍有原始数据可查。卡片的 60 条状态记录表示保留窗口内最近 60 次，而非另行永久保留 60 条。归档目标的旧明细也适用相同策略。

费用汇总表 `upstream_monitor_cost_rollups` 与业务账本 `upstream_finance_ledger` 不随保留期删除，也不外键依附当前厂家或目标。财务汇总同时读取未清理明细与历史小时汇总，监控成本、未计价数量、来源和利润口径保持一致；业务请求账本仍可按原精度查询。每个小时汇总另存实际首个／最后一个样本的精确时间，查询区间完整涵盖这些样本或与之完全不相交时可正常计算，因此永久删除当前小时的监控后，「截至现在」仍可正常查询。仅当半开区间 `[from,to)` 真正切穿某组已汇总样本的首末时间范围时，接口返回 `UPSTREAM_FINANCE_ARCHIVED_RANGE`，要求扩大到完整小时或日期，不把整个汇总费用冒充局部时段费用。UTC 整小时边界始终可查询；时区不是 UTC 整小时偏移时，可切换至 UTC 整小时边界查询这部分历史。

余额／倍率快照在保留期内完整保留；过期后，只额外保留每个目标**当前凭据身份**最近一次及最近一次成功观测。当前身份包含地址、协议、厂家、钱包标签、模型 Key 以及可选 New API 用户 ID／控制台凭据；更换 Key 后不会把旧 Key 的历史余额作为新 Key 兜底。旧身份的过期快照可清理；归档不会让这些快照永久无限累积。

归档仍表示停止调度并保留配置与历史。在存储管理的归档清单中可找到已归档厂家、分组／独立监控及智商／OAuth 计划；执行永久删除必须选择具体对象并输入其当前名称确认。永久删除厂家或目标前，监控明细仍先汇总费用，随后删除选中对象的配置、绑定和余额／倍率快照，历史业务账本与小时费用汇总继续保留。关联智商计划暂停并解除上游来源，已有作品保持各计划的保留规则；永久删除具体智商／OAuth 计划时才删除该计划及作品，并停用、失效其专用本地 API Key 缓存。正在检测、同步或有排队／执行中作品的对象返回繁忙，不强行中断。

清理删除的是数据库行。PostgreSQL 常规回收后可复用相应页空间，但数据库文件和操作系统看到的磁盘占用不保证立即缩小；该功能不执行会长时间独占锁表的 `VACUUM FULL`。容量判断应同时观察表大小、可复用空间与后续增长，而不是只看清理按钮后的文件尺寸。智商／OAuth 作品仍按每计划最近 20 条已结束记录保留，自动存储清理不会额外删除整计划或业务账本。

## 智商作品保留与 OAuth 执行

智商监控和 OAuth 监控共用 `/api/v1/admin/intelligence-monitors`，在 UI 中分为两个 Tab。任务固定使用 `gpt-6-astra`、`high`，提示词为 `创建一个 HTML，内容是用 SVG 绘制一个鹈鹕骑自行车的 2D 动画。你不需要任何测试。`。新计划定时默认关闭，开启后才参与调度；关闭浏览器不影响已排队任务。

全部智商来源默认最多等待 15 分钟，界面提供 5/10/15 分钟，API 接受整数 180–900 秒以兼容旧设置。迁移 `250_intelligence_monitor_generation_timeout.sql` 将已有 180–300 秒计划统一提升到 900 秒，仅改 `timeout_seconds`，保留启停、下次执行时间、`updated_at` 等其他配置；已排队、执行中及历史记录的超时快照不改，也不自动重放。任务租约按本次超时加 180 秒生成，15 分钟任务的租约为 18 分钟，防止旧 8 分钟租约提前结束正在生成的作品。

每个计划最近 20 条已结束执行（`succeeded`/`failed`）按 `created_at DESC,id DESC` 保留，横版卡片左新右旧。`pruneIntelligencePlanRuns` 在完成或租约过期事务内持有计划锁清理旧行；启动调用 `PruneRuns` 清理已有超量数据，归档计划也处理。超出部分的记录及 HTML/原始回复物理删除；`pending`/`running` 排除在保留删除之外，因此存在活跃任务时总数可暂时大于 20。此规则只适用于智商作品，不能套用于财务依赖的可用性监控记录。

OAuth 来源为 `openai_oauth`，迁移 `246_intelligence_monitor_oauth.sql` 加入 `account_id`。管理员选择站内已有 OpenAI OAuth 账号，名称跟随账号当前名称，运行快照保存当次名称与账号。服务端校验账号类型、固定模型能力、未重映射以及执行时可调度状态，拒绝影子/合成测试账号。

执行直接指定该账号传入正常 OpenAI OAuth gateway `Forward`，复用 Token 获取/刷新和代理配置，先获取账号与所选代理的并发槽；不可用代理排除后再选择，槽不可用则失败。没有按分组随机路由或自动改用其他账号的行为。超时/取消会结束后台请求；不把一次中断任务自动重发以避免重复费用。

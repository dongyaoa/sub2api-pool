# Intelligence monitoring

Private administrator APIs under `/api/v1/admin/intelligence-monitors` compare generated HTML artifacts using the fixed `gpt-6-astra` model, `high` reasoning and the fixed Chinese pelican-on-a-bicycle prompt. Plans are paused by default. Generation is asynchronous; new requests for a busy plan are rejected and at most two workers run globally.

Manual display order is persisted with `PUT /api/v1/admin/intelligence-monitors/plans/order`, body `{ "scope": "intelligence" | "oauth", "ids": [3, 1, 2] }`. The intelligence scope includes every non-OAuth source; OAuth is a separate list. IDs must form the complete current set of non-archived plans in that scope, without duplicate or nonpositive IDs; an explicitly empty array is valid only for an empty list. Invalid input returns 400 / `MANUAL_ORDER_INVALID`; changed membership or cross-scope IDs return 409 / `MANUAL_ORDER_CONFLICT` and require a fresh list. Success returns `data: null`. `ListPlans` array order is authoritative; no extra public sort field is required.

Migration `251_upstream_manual_order.sql` adds nullable display positions. Unordered entries retain `created_at DESC,id DESC`, following explicitly ordered entries. New plans append after saved positions; changing between OAuth and non-OAuth clears only the moved plan's position. Reordering changes only `sort_order`, leaving source configuration, version timestamps, schedules, billing and all run snapshots intact. It works while a generation is pending or running and does not enqueue anything. Shared membership locks exclude concurrent creation/archive/moves during validation, while a per-scope lock serializes list reorder requests.

Custom monitoring intervals accept integer JSON seconds from **30 to 86400**, default **3600 seconds**. All generation sources default to a **900-second (15-minute)** timeout; the API accepts integer **180–900 seconds** to preserve existing 180/240-second inputs. The UI offers 5, 10 and 15 minutes. Migration `249_intelligence_monitor_interval_seconds.sql` changes only the interval constraint. Migration `250_intelligence_monitor_generation_timeout.sql` raises existing plans with 180–300-second timeouts to 900 and changes the column default/check. It updates **only** `timeout_seconds`: enabled state, next/last run times, `updated_at` and all other settings remain unchanged. It never updates run rows, so already queued/running requests and completed history retain their captured timeout; requests are not replayed or retried. The next due time is measured from completion, not a fixed wall-clock frequency, and a short interval never permits overlapping generations for one plan.

Direct external and local-loopback HTTP clients allow 900 seconds for both response headers and the complete request. Each execution still uses its immutable run timeout, plus a 45-second outer allowance for source preparation; persistence has an independent 15-second budget. Claimed runs receive a lease of **captured timeout + 180 seconds**, including an 18-minute lease for a 15-minute generation, so a live job is not expired by the former eight-minute lease. Expired leases fail once and do not enqueue a replacement.

## Sources

Remote `upstream` and `external` requests use `stream:true` with an SSE/JSON Accept header. A bounded incremental reader stops on a successful Responses terminal or Chat Completions stop, or a failure terminal, without waiting for EOF. A bare `[DONE]` without a successful completion is insufficient. Complete JSON remains supported even with a stale SSE header. The 4 MiB limit includes all received event data and comments. HTTP and SSE failures keep only bounded, redacted JSON diagnostic fields and validated request identifiers; no raw error page or credentials are stored. There is no automatic replay or model/protocol fallback. Existing historical errors are unchanged.

`local_group` and `openai_oauth` keep buffered internal execution. Changing loopback requests to streaming would opt them into ordinary first-output and stream-idle guards, so their trusted long-generation path is preserved. Remote gateway/proxy timeouts remain outside the local worker deadline: receiving HTTP 502/503 does not prove that the local 900-second budget elapsed. Ordinary availability probes may use a different model and protocol and do not establish that the fixed high-effort generation route is healthy.

`external` stores an encrypted API key for a public HTTPS endpoint. `upstream` references an existing upstream target. `local_group` uses a dedicated restricted API key and the local gateway to preserve the selected group's actual routing and billing rules.

For `local_group`, a process-local single-use permit transfers the worker deadline across the loopback HTTP boundary. It is bound to the real key ID and key fingerprint, POST path, loopback peer and original deadline, expires/cancels with that worker, and is removed after dispatch. Normal API key, IP, account and billing authorization must succeed before the permit can be consumed; forged headers or user agents do not enable it. The internal header is stripped before forwarding. Only this authenticated monitoring context extends response-header and buffered OpenAI/native Anthropic stream-idle budgets to the generation deadline; ordinary traffic keeps its existing limits. Context detachment never removes the monitoring deadline or shutdown cancellation.

`openai_oauth` accepts `account_id` referencing a real OpenAI OAuth account. The plan name and current `source_name` come from the account; supplied names are ignored. This source always uses Responses. Shadow accounts and synthetic UI fixtures are excluded; the account must support the fixed model without remapping. Save, enable and execution all require `Account.IsSchedulable()`: active status, the scheduling switch enabled, no enforced expiry, and no active rate-limit, overload or temporary cooldown. The enable-only path applies the same validation; the pause-only path remains available even if the account has become invalid or disappeared. Execution additionally checks proxy availability and account/proxy concurrency. Invalid or unavailable accounts produce a failed record without trying another account.

For the account picker, request `platform=openai&type=oauth&status=active&lite=1`. The existing account-list `active` filter also checks the scheduling switch, rate-limit reset and temporary cooldown, but does **not** exclude overload or enforced expiry. The UI must also exclude future `overload_until`, `auto_pause_on_expired && expires_at <= now`, shadow and synthetic accounts. `expires_at` is Unix **seconds**; transient timestamps use RFC3339. The backend remains authoritative for current status and fixed-model support/remapping. Invalid source or interval configurations return HTTP 400 / `INTELLIGENCE_MONITOR_INVALID`, with metadata field `account_id` or `interval_seconds` and a safe explanation; malformed/noninteger JSON is rejected at binding.

The OAuth runner calls `OpenAIGatewayService.Forward` with the selected account. Existing token refresh, bound proxy, TLS and transport behavior are reused. A process-local context marker supplies a 900-second response-header allowance to separate normal/TLS transport cache entries; the run deadline remains authoritative, and ordinary requests retain the configured header timeout and their existing cached transports. No bearer/refresh token is copied into the monitoring tables or returned in monitoring DTOs. The gateway's internal protocol compatibility handling remains in effect; the monitor never retries a failed generation or enters the account scheduler. Background requests opt into cancellation on task timeout or service shutdown, and a maximum 4 MiB response. Source snapshots retain the selected account ID/name, OAuth marker and actual model/effort when available. OAuth does not pretend to have an upstream group billing multiplier.

## History retention

Each plan retains the latest **20 terminal records** (`succeeded` or `failed`), ordered by `created_at DESC, id DESC`. Older terminal rows, including HTML/raw text, are physically deleted. Active `pending`/`running` rows are excluded. Cleanup runs on service startup and transactionally after completion or expired lease handling, including archived plans.

Plan list responses include `recent_runs` (latest first, up to 20 terminal summaries) and `latest_run` (which can be pending/running). Full HTML/raw text remain detail-only via `/runs/:id`; generated documents must be previewed inside an isolated sandbox. Old record IDs return not found after retention removes them.

## Verification

Unit tests cover immutable prompt/effort, source validation, automatic account names, captured generation deadlines, isolated normal/TLS header allowances, cancellation, concurrency/proxy failures, response limits, source snapshots and retention scheduling. The OAuth integration test uses the real gateway with a fake HTTP upstream/token cache; it makes no model request. PostgreSQL tests use an opt-in `UPSTREAM_TEST_DATABASE_URL` and a private temporary schema to cover idempotent migrations, preservation of all plan metadata/run snapshots during the timeout upgrade, leases past eight minutes, global worker limits, expiry without replay, CRUD, account deletion, history persistence and physical retention.
